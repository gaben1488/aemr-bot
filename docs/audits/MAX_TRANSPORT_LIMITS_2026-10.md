# MAX: лимиты транспорта, проверка 30.10.2026

Сверены официальные страницы MAX и установленный из lock SDK
`maxapi==1.2.3`. Проверка локальная, без реального токена и отправки
в MAX. Успех модели/заглушки не подтверждает доставку или отображение
на клиентах платформы.

## Текст: официальный предел и ограничение закреплённого SDK

MAX указывает «до 4000 символов» для текста отправки и редактирования.
На этих страницах единица не уточнена как UTF-16. Поэтому утверждать,
что MAX официально задаёт именно 4000 UTF-16 code units, нельзя.

В установленном `maxapi/methods/send_message.py` и `edit_message.py`
конструктор проверяет Python `len(text) < 4000`: 3999 кириллических
символов проходят, ровно 4000 вызывают `ValueError` до сетевого запроса.
Это более строгая граница SDK. Эмодзи вне BMP при этом считаются одним
Python-символом, а не двумя UTF-16 единицами.

`utils/text_pages.py::fits_max_message` теперь по умолчанию разрешает
не более **3999 UTF-16 единиц полного сообщения**, включая служебную
шапку. Это консервативное правило приложения, совместимое со строгой
границей SDK, а не цитата из документации MAX. Регрессии вызывают
настоящие конструкторы SendMessage/EditMessage без сети, проверяют
3999/4000 кириллических символов и отличие учёта 2000 эмодзи.
Логические лимиты обращения 20 000 и ответа оператора 3000 не менялись:
они не являются лимитами одного транспортного сообщения.

## Вложения и загрузка

| Тип | Указанные MAX ограничения одного объекта |
| --- | --- |
| image | До 50 МБ и не более 7680 × 7680 px, оба условия; JPG/JPEG/PNG/GIF/TIFF/BMP/HEIC |
| video | До 250 МБ; MP4/MOV/MKV/WEBM |
| audio | До 256 МБ и не более 60 минут, оба условия; MP3/M4A и другие |
| file | До 4 ГБ; TXT/DOC/PDF и другие распространённые форматы |

Для группы изображений и видео **общее число вложений не более 12**,
включая не более одного `inline_keyboard`. Следовательно, при наличии
клавиатуры остаётся максимум 11 медиа. Файл типа `file` допускается
только один, с необязательной одной клавиатурой; смешивание с фото/видео
не поддерживается. Приложение разделяет фото/видео на группы, файлы
и аудио — по одному. Более консервативная одиночная отправка аудио
не выдаётся за разрешение произвольных смешанных альбомов.

Каждый объект предварительно загружается отдельно, одному токену
соответствует один медиафайл. Токен можно повторно использовать для
того же объекта. Альтернатива прямого URL предусмотрена для изображения,
но не аудио, видео или общего файла. Документация не подтверждает
какой-либо суммарный лимит в байтах для логического обращения из
20 файлов; такой предел здесь не обещается.

В SDK `maxapi/utils/upload_limits.py` размер проверяется предупреждением,
без запрета. Двоичные МБ/ГБ — явное допущение SDK: официальный источник
не уточняет десятичные или двоичные единицы. Разрешение и длительность
SDK не проверяет. `BaseConnection.upload_file` читает файл полностью
в память, поэтому серверные 4 ГБ не означают, что бот с ограниченной
памятью способен безопасно загрузить такой файл. Пересылка уже полученных
токенов не требует скачивания исходного содержимого ботом.

## Темп, повторы и неизвестный результат

MAX ограничивает отправку двумя сообщениями в секунду **в один диалог,
группу или канал**; отдельно указан общий бюджет 30 rps к API.
Процесс приложения применяет общий консервативный бюджет 1.5 send/edit
в секунду. Исправлена стартовая ёмкость bucket: 3 позволяла отправить
три запроса одновременно, теперь ёмкость 1 даёт слоты 0, 2/3, 4/3
секунды. Детерминированный тест реальных `_reserve` с фиксированными
монотонными часами воспроизвёл старый дефект и проверяет новые слоты.
Это политика резервирования, а не измеренная пропускная способность
или гарантия отсутствия 429: сетевые задержки могут сдвинуть поступление
запросов на сервер, ошибки самого лимитера остаются fail-open.

Сам SDK умеет повторять ошибки соединения/серверные ответы и
`attachment.not.ready`. В рабочем `main.build_bot` явно установлены
`max_retries=0` и `after_upload_attempts=1`, поэтому скрытые повторы
изменяющих запросов внутри SDK отключены. Явный отказ обрабатывается
приложением отдельно; тайм-аут не доказывает, что сообщение не отправлено.
Гарантия exactly-once, восстановления неизвестного результата по одному
тайм-ауту или порядка завершения нескольких редактирований здесь
не заявляется. Состояния неизвестной отправки требуют сверки с MAX
и служебной диагностикой; права на ручное повторение проверяются
отдельно по актуальному состоянию обращения.
